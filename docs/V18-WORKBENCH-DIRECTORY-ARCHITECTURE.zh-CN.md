# 18.0 工作台目录架构讨论稿

日期：2026-11-09（Asia/Shanghai）  
状态：历史讨论稿，保留当时的分析，不作为当前实现状态或实施契约。后续已进入 alpha18.0 实施阶段。  
基线：当前 main 工作树，包括 alpha17.6 的未提交实现。

实施依据为 [18.0 重构计划书](./V18-REFACTOR-PLAN.zh-CN.md)，最新残余问题与修复顺序见 [区域、会话与布局操作解耦核查](./V18-AREA-SESSION-DECOUPLING-AUDIT.zh-CN.md)。本文后续出现的“尚未实施”、旧格式迁移、单独 layout/context 主数据文件及待确认选项均属于历史讨论；与新计划冲突时，以新计划为准。现行约束为 `.bay/workbench.json` 单一工作台定义、不迁移 17.x 数据、区域项目与内页会话分离。

## 1. 用户提出的方向

1. 创建工作台时选择存放位置，在那里新建这个工作台的文件夹。
2. 创建区域时，选择工作台文件夹内部的已有文件夹，或者在内部新建文件夹。
3. 区域中新建对话，默认使用区域文件夹作为项目目录。
4. 用统一的目录归属支撑 Bay Agent、插件、工作成果以及整个工作台包的导出和导入。
5. 接收方导入整个工作台包后，目录、文件、对话历史和关联完整恢复，无需逐个重新绑定对话，可以继续工作。
6. Bay Agent 直接使用工作台根文件夹作为项目目录，在其中持久化存储和更新该工作台专属记忆；记忆随完整工作台包迁移。

这比上一版“区域绑定任意现有项目”的建议更进一步：工作台本身拥有根目录，区域项目受到工作台根目录约束。本稿作为上一份[区域项目绑定讨论稿](./AREA-PROJECT-BINDING-PROPOSAL.zh-CN.md)的上层设计；上一稿关于内页绑定、任务继续、插件来源和多对话迁移的分析仍然适用。

已确认的任务策略继续有效：同一任务优先续用原对话，新任务另建；对话失效或需要隔离时允许另建。

## 3. 核心关系与身份

```text
工作台：稳定 workbenchId + 本机根目录关联
  Bay Agent Main：根目录 Workspace + 持久主对话 + 工作台专属记忆
  区域：稳定 areaId + 根目录内 relativePath + 分工背景
    原生项目：本机 Workspace，与解析得到的目录对应
    对话内页：精确 Session 绑定
    插件内页：项目绑定、具体 Session 或资源绑定
```

推荐把根目录的绝对位置保存在本机登记中，把区域位置保存为相对路径。例如同一个区域持久保存 `projects/app`，本机解析为 `D:/Bay/演示工作台/projects/app`，换机后可以解析为 `/home/user/Bay/演示工作台/projects/app`。

文件夹名称、区域显示名、工作台显示名与稳定 ID 分开。更改显示名不自动重命名磁盘目录。根目录整体移动后通过“重新定位”恢复，不凭旧绝对路径创建空替代目录。

根目录是一条文件组织边界，不意味着 Worker 自动具备或被禁止访问任何其他路径；实际工具访问继续遵循 Host 的权限和执行环境。

## 4. 文件布局与数据来源建议

下面是示意布局，`projects`、`outputs` 不是硬编码的强制目录名；区域可以选择根内其他普通子目录。

```text
我的工作台/
  .bay/
    workbench.json             工作台身份、区域目录映射与格式版本
    layout.json                可持久的区域和内页结构
    context.json               带 revision 的结构化背景
    context/
      工作台整体背景说明.md
      areas/<areaId>/区域说明.md
    memory/
      index.md                 简短记忆索引
      facts.md                 已核验的长期事实
      decisions.md             已确认决策与原因
      progress.md              当前阶段和交接摘要
      areas/<areaId>.md        按区域整理的知识
    sessions/                  导出/恢复快照中的原生会话日志
    attachments/               会话引用的图片与文件
    orchestration/             任务、执行历史与检查点的可迁移快照
  projects/
    app/
    research/
  outputs/
```

建议新文件型工作台的定义、布局、背景以目录内受 Host 管理的数据为持久来源；Profile 保留本机路径索引、最近打开/窗口偏好、原生 Workspace/Session 映射、凭据与运行状态。旧 Settings 适配器读取 Host 投影，不能和目录文件各自维护一套可写主数据。迁移到这个来源划分应作为独立实现切片。

`memory` 是工作台内实际持久文件。`sessions`、`attachments`、`orchestration` 在生成完整导出/恢复快照时物化，并写入一致的清单与快照边界；活动 Session 仍由原生服务作为单一写入方管理，不同时让插件和原生持久层各写一份活动日志。这样完整导出目录具有恢复所需数据，而运行时不会出现两套日志互相覆盖。

背景继续保留现有 human/agent 区段、revision 与写入接口。首版建议 `context.json` 是结构化来源，Markdown 是同版本可读投影；磁盘 Markdown 直接编辑若要生效，需要单独定义解析、变更检测和冲突合并，不能与 JSON 静默双向覆盖。现有界面手工填写、单轮 AI 草稿、Bay Agent 允许区段写入均通过统一 Host 服务更新。

区域背景按 areaId 存放，而不直接覆盖项目子目录里一个固定名称的文件。这样两个区域共用同一项目时，仍能保留不同分工背景。

`.bay` 是内部元数据目录，不能被选作普通区域项目目录。插件持久配置进入工作台定义，插件依赖仍通过已有分发能力恢复；不把整个宿主安装目录复制进工作台。

## 5. 创建和日常操作

### 新建工作台

- 用户选择父目录，输入工作台名称，界面展示将创建的完整目录。
- Host 创建新的工作台目录和初始定义，再登记工作台；相同请求重试返回相同结果。
- 目录重名时提示更换或明确选择已有工作台打开，不直接覆盖已有文件。
- 若文件创建与 Settings 登记之间失败，保留可恢复的操作记录；不能把半完成状态报告为创建成功，也不能清理用户已有目录。
- 先只创建工作台，不为每个预设区域批量创建对话。布局预设中的空区域可以显示待选文件夹状态。

### 新建区域

- 提供“选择工作台内已有文件夹”和“在工作台内新建文件夹”。
- 保存区域相对路径，独立登记/复用原生 Workspace；此时不必创建 Session。
- 一个区域拥有一个默认项目目录。多个区域共用同一个根内目录是建议允许的能力，仍待产品确认。
- 路径归属由 Host 检查，包含 Windows 大小写与目录联接、符号链接解析；不能只检查字符串前缀。指向根外的链接不自动变成工作台内的受管项目。

### 新建与继续对话

- 区域中新建对话默认使用区域对应的 Workspace，只需选择模式等必要信息。
- 打开已有对话时核对项目归属；首版建议保持同区域同项目，跨目录任务放到对应区域。
- 延续已确认的任务策略，并给 Worker 原生 Session 和内页设置任务标题。
- 更改区域目录不能直接改变已有 Session 的 cwd；有执行或既有对话时走明确的迁移/新区域流程。
- 关闭/归档区域和移除工作台入口不删除项目文件；文件夹删除是独立操作。

## 6. Bay Agent 和插件

Bay Agent 通过 Host 的语义接口创建/查看工作台内目录、创建绑定目录的区域、读取区域结构、创建或继续任务。建议输入 `workbenchId + relativePath`，由 Host 决定真实路径与 Workspace，不依赖模型拼接绝对路径。

示意接口包括 `createArea({ relativePath, createDirectory, ... })`、`inspectDirectories()` 和继承区域目录的 `dispatch()`；名称和签名尚未定稿。普通 UI 与 Agent 共用同一服务，保持重复请求、归属和并发校验一致。

用户已明确：Main 的项目直接使用工作台根目录，Worker 默认在区域目录执行。必须将根目录登记为 Main 对应的原生 Workspace，并为 Bay Agent 配置所需文件/记忆接口；现有代码没有这一目录保障。Main 仍是工作台持久会话，位于已有浮动工作区。

插件分别接收项目级和 Session 级来源。轨迹、终端、审查等当前原生能力依赖具体 Session，新增目录模型不能让它们随活动对话悄悄改绑。纯项目文件浏览如果希望在零 Session 时使用，需要新的项目级服务适配。

同一文件夹中的两个 Worker 共享文件写入范围；不同子目录也可能属于同一个 Git 仓库。目录划分并不自动提供文件冲突隔离。18.0 首版应保留任务协调，同文件并行修改需显式分工；自动 worktree 隔离可以另行扩展。

### 工作台专属记忆

背景表达人的目标、约束和区域分工；记忆表达 Bay Agent 在执行中积累并核验的知识、决策依据、成果位置和交接信息；Session 日志保存原始对话，编排账本保存任务执行事实。记忆引用任务、区域或文件作为依据，不能覆盖原始账本，也不能把模型猜测当作已确认结论。

建议首次打开/恢复 Main 时读取简短记忆索引和当前阶段摘要；每次模型调用带入有界摘要及版本信息，具体任务再按需读取相关条目。不能每轮把所有历史和记忆文件全文注入。Worker 只获取当前任务、工作台/区域背景和相关记忆片段。

建议在任务验收、用户确认重要决策、发现并验证长期事实、阶段交接时更新记忆。通过工作台记忆接口写入，带版本冲突检查与可追溯记录；允许人查看、修改和移除。工作台背景为空时保持为空，记忆服务不自动替人编造目标。记忆变更不能扩大 Agent 权限或改写人的约束。

导入后保留 Main 对话和记忆，重新注入接收方实际根目录/项目映射。保留来源信息；对依赖旧机器环境的事实标记需要重新核验。

## 7. 整个工作台包的语义

**用户明确的主验收对象是“完整工作台包”：目录、文件、对话、附件、内页关系、Bay Agent 记忆都能导入恢复并继续使用。** 模板包可保留为轻量选项，但不作为完成 18.0 完整迁移目标的替代品。

| 导出方式 | 内容与用途 |
| --- | --- |
| 工作台模板 | 布局、背景、目录结构、插件声明、对话模板等；接收方填入自己的工作内容 |
| 完整工作台包 | 全部受管目录和工作文件、布局、背景、Main/Worker/用户对话及被引用的子会话、附件与资源、插件可迁移配置和依赖、任务/编排快照、工作台专属记忆；用于直接接续工作 |

完整包按根目录相对路径记录文件及摘要，保留空目录和共享目录映射，不对同一目录重复收集。对话收集按工作台所有权和显式引用计算，不能仅导出当前活动标签；已关闭内页但仍属于该工作台任务的 Worker、Main 和相关子会话也要被覆盖。现有 online-reference/offline-embedded 仍表达插件交付方式；完整离线交付必须携带可以分发的所需制品。

导出前展示完整性检查、文件范围与大小。任何排除项都必须明确，不能悄悄省略对话引用的文件、附件或恢复所需数据并报告“完整”。Profile 中的模型账号和机器进程状态不进入工作台文件闭包；接收方使用自己的模型连接。工作文件、隐藏文件与可重建缓存的具体选择规则仍需细化。

导入时用户选择目标父目录并完成必要环境配置，其余关系自动恢复：先校验包和快照一致性，恢复目录/文件/附件，再建立本机 Workspace、Session 与资源映射，写入并校验原生会话，恢复所有区域、内页、Main、记忆及任务关联，最后登记并打开工作台。完整包不要求逐个选择本地对话。旧模板包可以继续使用手工绑定流程，但应清晰标识。

原生会话迁移适配器是 18.0 的必要组成部分：

- 保存完整已提交事件、标题、模式、fork 继承边界、子会话关系、模型配置提示以及图片/文件附件。
- 分别维护包内身份与接收方本机身份，自动重建 cwd、Session/Workspace/内页/任务关系；同一来源 Session 的多个视图仍关联到同一个导入 Session。
- 按事件和资源的结构化契约重映射引用，历史文本中的旧路径保留为历史事实；运行时定位使用新映射，不能在整份历史上盲目替换字符串。
- 需要恢复的插件状态和资源引用必须有兼容处理器；缺少依赖或引用时明确报告完整性问题，不以空白对话替代。
- 已有的 Session 压缩/替换事件和继承历史要一起迁移，确保显示历史与模型可用上下文均可重建；导入后实际发送一轮消息作为验收。
- 读取前建立持久化屏障，固定会话事件边界与工作文件快照；活跃任务可暂停至可导出的边界。逐文件复制一个持续变化的目录不能声称一致快照。

接收方恢复的是完整可继续工作的持久状态。正在执行的工具进程、连接、未完成原生授权不能被当成仍在原机运行；任务保留检查点和关联，以待继续/待接管状态展示，继续时使用接收方环境。导入历史本身不能重放历史工具调用。

打开移动后的原工作台保留身份；把完整包导入为副本创建新的本机身份并恢复 Main 的已有历史及记忆，记录来源，避免两个副本误用同一主会话或任务状态。导入得到新的本机 Session ID 不应丢弃旧对话内容。

## 8. 旧工作台迁移

已有工作台继续兼容打开，不在升级时自动移动用户的项目目录。迁移向导先选择新根目录，再为原区域选择根内目标目录，明确哪些文件复制或重新绑定。完成后验证原生项目、会话来源、背景和任务关联。

旧 Session 的 cwd 不会因布局字段更新而改变。迁移应复用完整包的会话迁移适配器，保持原日志完整，在新目录映射下重建可继续的 Session；不通过改布局字段宣称完成会话迁移。无法完整迁移的工作台保留原数据及旧格式兼容状态，明确列出阻碍，不以空会话替代历史。

导入旧布局包、已有混合项目区域、根目录失联、复制出同 ID 的目录、切换不同 Host，都需要相应诊断和恢复路径。

## 9. 建议的 18.0 实施切片

1. **完整迁移技术验证与契约**：用含工具历史、图片/文件附件和子会话的小样本先验证原生历史导出、换目录导入、引用重建与实际续聊，同时定义根目录、身份和单一持久来源。
2. **创建闭环**：创建工作台目录、区域选/建子目录、零 Session 项目绑定、Main 使用根目录、Worker 继承区域项目；保存重开可恢复。
3. **多对话、记忆与编排闭环**：统一 UI/Agent 路径、独立内页绑定、任务命名与复用、记忆读写和有界读取、插件来源、执行有效性和 Attention。
4. **完整包与迁移闭环**：一致快照、文件与附件清单、所有权/引用闭包、原生会话自动恢复、Main/记忆/任务关联恢复、旧工作台迁移和失败恢复。
5. **验收封包**：在没有发送方 Profile 的接收机器导入，核对目录与文件摘要、Main/Worker/用户会话历史、图片附件、资源定位、记忆和布局；在导入的普通会话和 Main 中继续一轮，再恢复一个中断任务。

完整包验收还需要覆盖：重复导入为独立副本、根目录变更、缺失附件/插件的完整性报告、长历史 checkpoint、导入过程失败重试不重复创建 Session，以及导入不触发历史工具重放。

这是一轮范围可控的基础模型重构，涉及持久化与包协议，不能只在创建表单添加一个 path。已有布局 UI、原生对话渲染、背景单轮服务、事件账本与 checkpoint 可以作为基础继续使用。

## 10. 仍需对齐的选择

- 多个区域是否允许共用一个根内文件夹：建议允许，区域背景按 areaId 独立保存。
- 完整包的文件筛选与可重建缓存策略：必须满足目录、对话和资源完整性目标，排除项可见。
- 背景 Markdown 是否需要支持外部编辑即时生效：首版建议由统一服务生成投影，外部编辑能力另定契约。
- 旧外部项目迁移时采用复制、重新绑定还是保留兼容状态：不自动移动，按实际项目逐项选择。

完整工作台包、Bay Agent 根目录和专属记忆已由用户明确要求；本文前面的讨论保留设计演进记录，当前实现状态以计划书和以下段落为准。
