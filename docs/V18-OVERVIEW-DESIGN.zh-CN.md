# 18.0 工作台总览、原版侧栏与浏览器管理：设计及实施记录

日期：2026-11-10。

状态：2026-11-10 已实施产品代码，完成自动回归、类型检查、RC.1 兼容检查、构建和浏览器组件检查；尚未在安装后的 DSH 中完成真实侧栏点击、跨端交接及输入发送验收。本轮不提交、不封包。此前的交互讨论稿仍是示例原型，产品实现与验证范围见文末。

## 已确认的布局方向

用户选择“工作台列表与选中工作台详情并排显示”。合并原有“全部工作台”和“工作台管理”的重复列表。

- 左侧负责工作台检索与选择；选择不等于进入工作台。
- 右侧保留名称、简介、根目录和打开／返回入口，下设概览、区域与内页、背景与记忆、分享与迁移。
- 概览优先展示需要处理的事项、实际布局预览和继续原会话的入口；缺少内容时使用明确的空状态。
- Bay Agent 展示状态与任务入口，聊天仍使用原有浮动工作区中的持久 Main。
- 全局交互偏好、内页分类仍放在全局设置；工作台自身数据放在选中详情中。
- 完整工作台包、布局与扩展分发、浏览器访问、局域网协作使用不同入口和准确的范围说明。
- 首页按需加载轻量摘要，不因查看总览而加载全部会话历史或启动 Agent。现有 updatedAt 不能直接当成最近工作时间。

## 新增需求：固定到 DSH 原版侧栏

工作台列表条目增加 Pin 图标按钮，命名“固定到 DSH 侧栏”，固定后变为“已固定到 DSH 侧栏”，再次点击取消。

这里的固定表示桌面原版导航快捷入口，独立于现有 `pinnedAt` 工作台列表置顶。按钮与选择工作台是两个独立的可聚焦控件，避免嵌套按钮；点击 Pin 不进入工作台。

固定后，在 DSH 原版左侧“插件”“自动化任务”等全局导航入口所在位置增加以工作台名称命名的入口，使用工作台图标。点击直接打开这个工作台，沿用原区域、原布局与原会话。

固定状态与导航选中态分开。原版正在显示普通会话时，工作台快捷入口不因为已经固定就显示选中高亮。

## 侧栏实现契约

### 身份与持久化

- 在本机 Profile 的设置根层保存 `sidebarShortcuts: string[]`；这是本机偏好，不是 `.bay/workbench.json` 定义字段。
- 使用工作台稳定 ID 生成命名空间内的面板 ID，例如 `dsh-bay.workbench.<workbenchId>`。显示名和路径不作为注册身份。
- 只为用户固定的工作台注册导航入口及承接页面；取消固定注销这一对注册。
- 固定偏好不写入工作台背景，不与 `pinnedAt` 混用，不随完整工作台包给接收方自动安装侧栏入口。
- 不读取或修改 DSH 私有 Pin 存储，不覆盖 `entry-customization`，不替换 `sidebar` owner。
- 现有工作台投影过滤官方 More 的策略与原版侧栏保持独立。该功能不需要借机放开工作台内的所有官方 More 入口。

### 点击与生命周期

1. 宿主数据准备就绪后，依据持久偏好和有效工作台登记建立注册。
2. 导航入口可用之前，确保对应 `main` 承接页面已注册。
3. 承接页面只负责导航，不创建另一份工作台渲染器、Session 或 Bay Agent。
4. 使用同一工作台打开操作，完成目录核验、未保存状态处理、主控检查和 `openAndSelect`，再进入／展示目标工作台。
5. 明确切换总览的 `surfaceView` 为工作区，不能只把模式改成 workbench 后停在总览。
6. 当前 `mode-controller.ts` 的 `enter()` 在已经处于 workbench 模式时会直接返回，因此不能把它独立当成“切换任意工作台”的完整接口。当前实现通过 `directory.openInSurface` 组合现有目录打开与界面导航能力。
7. 承接页面处理成功后恢复合适的原版面板选择；退出工作台时不能因快捷承接页重新挂载而马上又进入工作台。重复点击、React 重挂载和上游重载不能重复触发导航。
8. 打开失败展示原始原因与重试／返回；不得偷偷新建空工作台或会话。

### 边界行为

| 变化 | 快捷入口行为 |
| --- | --- |
| 修改工作台名称 | 保持注册身份，更新显示名称 |
| 关闭工作台标签／未打开工作台 | 保留快捷入口，可再次打开 |
| 取消侧栏固定 | 仅移除导航入口；项目、工作台、会话与运行任务保持各自生命周期 |
| 归档工作台 | 暂不注册入口，保留本机偏好；恢复后再显示 |
| 移除本机登记 | 清理关联的快捷入口偏好与注册 |
| 根目录丢失／定义损坏 | 显示明确原因并提供定位／管理入口，不创建替代目录 |
| 浏览器正在主控 | 沿用当前交接规则，提示浏览器状态或收回入口，不静默抢占 |
| 插件／侧栏重载 | 从持久偏好恢复，每个工作台仅一个入口 |
| 导入一份工作台副本 | 默认不固定，由接收方主动选择 |

本轮只在总览提供固定管理。若后续需要在原版“更多”里管理这些入口，另用自有 id 追加一个 Bay 菜单区，并写入同一份 Bay 偏好；不可直接依赖只活在内存里的原生 Pin 回调。

## 侧栏验收清单（自动化覆盖及实机边界见文末）

- 固定／取消固定立即更新原版侧栏，并在插件和应用重启后恢复。
- 两个同名工作台独立注册，重命名不重复注册。
- 关闭标签不移除快捷入口；归档、恢复、移除登记按约定更新。
- 由原版快捷入口进入准确的工作台；原版与工作台往返后可以实际输入并发送。
- 退出不会自动重新进入；快速连续点击、重复挂载不重复创建对象。
- 根目录不可用、未保存修改、浏览器持有主控时正确处理。
- 原版侧栏先于／晚于 Bay 加载与重新加载时不出现残留、重复或缺少 main 的入口。
- 导出／导入工作台包不传播本机侧栏固定偏好。

产品代码及插槽契约测试已落地。真实 DSH 原版侧栏、安装后应用重启与实际发送仍待实机验收，不能把模拟插槽测试描述成安装验证。

## 浏览器接管期间的桌面管理页与收回反馈

新增需求：浏览器打开工作台后，桌面客户端的管理页应沿用新的总览设计；收回时显示进度条和当前操作说明。

### 管理页的信息层级

- 标题使用“工作台管理”与工作台名称，首屏隐藏 `Workbench Host`、稳定 ID 等内部标识。
- 首要信息为“当前在浏览器中使用”、连接状态和“收回到 DSH 客户端”。布局保存状态必须明确来源，只显示确实观测到的结果。
- 展示最近已保存的工作区布局缩略图与区域／内页入口。不能把它声称为实时浏览器画面。
- 局域网协作、工具与扩展作为次级管理入口。未开启分享或未接入工具时使用简短空状态，不展示整排 0。
- 详情分为运行概览、区域与内页、局域网协作、工具与扩展、运行诊断。
- `HTTP`、`WebSocket`、`Presence`、编辑器挂载数、`committed`、内部 ID、错误代码和原始指标移至诊断；业务状态转换为可读中文。
- 浏览器主控、局域网访客连接、后台任务各自独立呈现。收回主控不等同于停止分享或停止已授权任务。
- 复用现有工具开关、访客管理、权限设置与诊断能力，不能在界面重做时遗漏。

### 实施前发现及本轮修复依据

1. `WorkbenchBrowserControlPage.tsx` 概览直接呈现编辑器 outlet、layoutSaves.lastStatus 与连接计数，且未分享时仍展示整行 0。
2. 同一文件的 `canReclaim` 以没有分享 session 为条件；`WorkbenchFrame.tsx` 中 requestReclaim 再次要求先停止局域网分享。这与之前已经确认的“正常交还不停止分享”不一致。
3. `WorkbenchBrowserControlPage.tsx` 的收回处理没有检查 requestReclaim 返回的 boolean，调用结束后仍显示等待说明。`WorkbenchFrame.tsx` 也没有处理 windowController.reclaim 返回的 failed 结果；不能仅靠是否 throw 判断成功。
4. 桌面 `browser-window-controller.ts` 向 Host 提交 reclaim，然后每 2 秒查询确认，等待窗口约 30 秒。浏览器 `resolve-browser-window-view.ts` 通过 15 秒心跳读取 reclaim-requested，随后保存并确认。浏览器自己发起的路径有本页 wake，但桌面发起路径没有同等的即时通知。等待可能来自浏览器尚未收到请求，不等于正在保存。
5. 宿主 `host-browser-window-controller.ts` 收到浏览器 reclaimed 确认后释放主控；桌面随后读取并恢复浮动标签。这个 reclaimed 状态不表示所有桌面区域和会话输入引用已经就绪。
6. 当前窗口控制器在状态为 reclaiming 时再次 reclaim 会携带 force。重试与强制收回必须改为不同动作，不能用重复点击隐式升级。

上述问题已在本轮产品实现中处理。已通过真实文件型工作台服务与两端控制器的集成测试；该测试不等同于 DSH 桌面与外部浏览器实机交接。

### 进度展示契约

收回期间使用固定位置的进度面板，显示当前操作的一行说明、按步骤完成的进度条、可展开的详情。采用已完成步骤计数，不展示预计耗时百分比。

| 阶段 | 用户看到的说明 | 推进依据 |
| --- | --- | --- |
| 确认连接 | 正在通知浏览器准备交还工作台… | Host 接受请求，并收到目标浏览器的准备回报 |
| 保存状态 | 正在保存浏览器中的布局和内页状态… | 现有 Frame flush 完成，浏览器按约定报告状态 |
| 交还控制 | 正在同步浮动标签并交还控制权… | Host 验证交接快照和身份，确认撤销旧主控 |
| 恢复桌面 | 正在恢复区域、对话和浮动工作区… | 桌面读取最新定义、恢复浮动状态并建立视图引用 |
| 检查就绪 | 正在检查当前对话是否已准备好继续输入… | 当前工作区与可见会话的输入依赖就绪后完成 |

实现时将阶段作为跨端交接状态的一部分回报，不能在页面中用定时器自动跑到 100%。浏览器尚未响应时停在确认连接，不能提前宣称布局已保存。

- 将主控已交还与桌面已就绪分成两个事实；进度完成必须覆盖桌面恢复。
- 某个扩展内页单独加载失败时明确显示“已收回，部分内页暂不可用”，保留对应重试，不无限等待隐藏内页和所有扩展。
- 一次收回使用稳定操作身份，关联工作台、窗口与执行代次；旧操作的迟到阶段不能覆盖新的收回。
- 请求去重，切换总览或其他工作台不取消收回；返回时继续展示同一操作状态。
- 优先通过现有连接提供及时的收回通知和阶段回报，保留心跳作为失联检测与补偿。不能通过虚假的进度遮盖 15 秒通知延迟。
- 保存失败停在对应阶段；无响应显示等待状态和实际原因。普通“重试／继续等待”不能携带 force。
- 强制收回是单独明确的操作，说明使用最后已保存状态，可能无法带回浏览器尚未提交的修改；成功后仍保留“最新修改未确认”的结果说明。
- 浏览器页面显示对应的交还状态。确认失去主控后禁用旧页面写入；不把已经开始的 Agent 执行重新运行一遍。
- 正常完成后自动回到桌面工作区，并给出简短完成提示；原版／工作台切换后的输入能力属于验收项。

### 补充验收（实机验收清单）

- 浏览器正常响应、慢响应、后台标签节流、无响应、保存失败、回执丢失、桌面恢复失败分别有准确阶段与可用恢复入口。
- 收回期间重复点击不产生多个操作或强制升级；修改、切换视图不混淆工作台身份。
- 局域网分享开启时仍可正常收回，分享与已授权后台任务按既定策略继续。
- 进度不会在桌面尚未恢复时显示完成，失败也不会显示成功或一直笼统等待。
- 实际完成一次输入和发送验证；不能用静态输入框存在代替就绪。

交互讨论稿中的阶段通过本地模拟推进，仅用于体验正常交接、未响应和保存失败的展示，不代表真实产品已经接通这些事件。


## 2026-11-10 产品实施记录

### 总览与管理入口

- `WorkbenchHome` 改为工作台列表与选中详情并排；窄容器改为上下排列。选择、打开、侧栏固定相互独立。
- `WorkbenchOverviewDetail` 提供概览、区域与内页、背景与记忆、分享与迁移。直接显示根目录、区域/内页/独立会话数量以及保存的实际布局，点击缩略区域进入对应详情。
- 区域详情包含关闭的区域和重新显示入口；会话统计读取持久会话目录，不以打开的标签数量替代会话数量。
- 背景编辑继续调用原有范围明确的单轮生成服务，记忆在打开对话框时才读取。完整迁移入口与布局/扩展分发入口分别说明内容范围。
- 统一“全部工作台”与原管理列表；工作台资料保留原编辑表单，全局交互偏好与内页分类继续进入工作台设置。
- Bay Agent 卡片本轮展示已保存的主会话关联及模型配置，提示进入原有浮动工作区继续。**尚未增加总览中的实时任务/Attention 面板**，也不把已关联会话描述成正在运行。

### 侧栏注册与本机偏好

`client/workbench-sidebar-shortcuts.tsx` 为每个固定工作台注册 `dsh-bay.workbench.<id>`。先注册同 ID 的 `main` 承接页，再注册 `sidebar.panellist`；重命名、归档、恢复、注销以及上游插槽重载均更新这对注册。

导航经 `directory.openInSurface` 进入原有工作台：先处理未保存内容，再打开定义、进入工作台模式并切换到工作区。成功后清理原版临时选中面板，避免退出后再次自动进入。相同目标正在进行的导航共用一个 Promise，覆盖 StrictMode 效果重放。导航失败保留原始原因并提供重试。

`sidebarShortcuts` 与 `pinnedAt` 分开。本机宿主重启后保留；归档隐藏入口但保留偏好；移除登记清理偏好；取消固定不删除项目、会话或任务。宿主文件测试确认修改固定偏好不会改写 `.bay/workbench.json`。

### 浏览器管理与交接进度

管理页使用连接概况、最近保存的布局和明确的主操作；局域网分享、工具、区域详情与运行诊断继续保留。内部连接字段与原始计数集中到诊断页。

跨端进度使用 `WorkbenchReclaimProgress`：

| phase | 已完成步骤 | 更新来源 |
| --- | --- | --- |
| `notifying` | 0/5 | 桌面提交收回请求 |
| `saving` | 1/5 | 浏览器收到通知，开始 Frame flush |
| `releasing` | 2/5 | flush 成功，提交浮动状态与交还回执 |
| `restoring` | 3/5 | Host 已释放主控，桌面读取状态并刷新目录/会话 |
| `checking` | 4/5 | 桌面挂载区域与当前可见会话 |
| `complete` | 5/5 | 当前可见的绑定会话输入组件就绪 |

- Host 新增经过原页面凭据核验的 `watch-reclaim`（最长 5 秒长轮询）和 `reclaim-progress`。收回事件立即唤醒等待请求，15 秒心跳继续承担失联检测及补偿。

## 2026-11-10 追加：浏览器直接关闭后的恢复

补齐直接关闭标签页的完整恢复链路。`closed` 与正常交还共用浮动状态、目录/会话刷新及输入就绪检查；宽限期内主动收回立即完成 Host 释放，已关闭视图不再被“尚未就绪”拒绝；自动恢复期间点击收回加入同一次操作。关闭通知采用有界快照与小型信号补偿，避免浮动状态超过 Beacon 额度后丢失关闭信号。

自动恢复保留 10 秒刷新宽限期，约 10—12 秒进入恢复。界面区分“已保存状态恢复”与正常完成保存的交还，不承诺关闭前尚未提交的修改已经保存。详细原因与真实 Chrome 验证见 [浏览器/LAN 计划的第 11 节](./V18-BROWSER-LAN-REFACTOR-PLAN.zh-CN.md#11-2026-11-10关闭浏览器标签页后的收回修复)。
